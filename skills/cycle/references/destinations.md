# Choose the authoritative destination

Start from a named project and the outcomes the user selected. Check the applicable memory rules before reading or writing anything else. If those rules designate a particular memory owner or prohibit persistent capture, follow them. A request to summarize work can finish with an in-chat summary.

| Record | Evidence to check | Update |
| --- | --- | --- |
| Project status | Revision, artifact or command output the project owner can reopen | Update the existing milestone or append a correction with its date. |
| Selected Obsidian notebook | Selected vault, relevant index and an existing topic note or alias | Store durable reasoning in the appropriate section. Reuse the topic link. Keep transient test output with the project. |
| Existing Orca item | Matching project, item ID and current state through the available native item interface | With authorization, update the existing decision, blocker or next action. Read it back. If only a local export is available, prepare a proposed update and label the live item pending. |

For example, a formatter produced the approved byte sequence. The manifest verifies the outcome. Record it in the project status. If the team chose a different format because a reader cannot open the old one, that reasoning can belong in an explicitly selected knowledge note. The unresolved release date belongs on the existing work item. Keep one substantive entry per fact.

Before adding anything, look for an equivalent fact with the same evidence and scope. A repeat request can finish with the three existing references and zero edits. A later contradictory run calls for a dated correction, preserving what was true of the previous revision. Skip personal content outside the selected evidence and report exactly which destinations were verified.
